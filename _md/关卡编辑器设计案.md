## 0. 这个工具是干什么的

一句话：**让策划在一个可视化界面里，用鼠标画出关卡，然后存成一个文件、能一键测试。**

它只做三件事：

1. **画** —— 把鼠标操作变成关卡数据
2. **查** —— 保存前自动检查关卡有没有低级错误
3. **试** —— 一键运行，立刻试玩

它**不做**的事：

- 不做"游戏里的编辑器"（玩家看不到它）
- 不管玩法逻辑（它不知道什么叫"推箱子"，只知道"这里放了一个箱子"）
- 不改动 Unity 本身

---

## 1. 先看懂几个词

| 词 | 通俗解释 |
|---|---|
| **Unity 编辑器** | 你平时打开 Unity 看到的那个界面（场景、Inspector、Project 窗口） |
| **编辑器扩展** | 用 Unity 官方提供的接口，给编辑器**加**一个自己的面板/工具。类似给浏览器装插件，不是改浏览器本体 |
| **程序集 / Assembly** | 一堆代码打包成的文件（.dll）。Unity 会把脚本自动分到不同包里 |
| **编辑器程序集** | 只在编辑器里跑的代码包，**不会进最终游戏** |
| **ScriptableObject / 资产 .asset** | Unity 里一种"数据文件"，能在编辑器里创建、点开、编辑。我们用存"类型定义" |
| **Prefab** | 做好的模型/物体模板，可以反复实例化 |
| **体素 / 格** | 世界的格子。每个格有坐标 (x, y, z)，y 表示高度（第几层） |
| **注册表** | 一张"所有可用东西的清单"。工具照着清单显示按钮 |
| **连线 (Link)** | 把两个东西关联起来，比如"这个按钮被踩 → 那堵墙打开" |
| **JSON** | 一种纯文本数据格式，人能看懂，Git 也能比较差异 |

## 2. 它在项目里以什么形式存在

它**就是一堆文件**，放在 `Assets/` 里面，和普通脚本一样会被提交到 Git。

不同点是**编译位置**：

| 你的脚本放哪 | 属于哪个代码包 | 能进游戏包吗 |
|---|---|---|
| `Assets/Scripts/Manager.cs` | 普通运行时包 | ✅ 会 |
| `Assets/.../Editor/` 里的脚本 | 编辑器专用包 | ❌ 不会 |

判断规则很简单：**文件夹叫 `Editor`，里面的脚本就只有编辑器能用。**

为什么这样分？因为编辑器脚本会用到 `UnityEditor` 这个命名空间（画面板、画网格、撤销等功能都在里面），而这个命名空间**在打包后的游戏里不存在**。所以必须分开，避免打包报错。

**所以我们的工具 = 一组放 `Editor` 里的脚本 + 一组 `.asset` 数据文件。**

- 脚本：画界面、响应鼠标、存文件
- `.asset`：定义"有哪些类型的东西可以用"

## 3. 关卡数据长什么样

一个关卡，说白了就是四张清单：

| 清单 | 记什么 | 例子 |
|---|---|---|
| **实体块层** | 哪些格是实心的（地板/墙/坡） | "3,0,2 是墙" |
| **物件层** | 可推动的东西 | "箱子在 2,0,1" |
| **标记层** | 静态的点 | "出生点在 0,0,0"、"抵达点在 2,0,3" |
| **连线层** | 机关之间的关系 | "按钮A → 打开 墙B" |

存成 JSON 大概长这样（示例，实际字段以程序为准）：

```json
{
  "id": "1-1",
  "name": "第一步",
  "size": { "x": 5, "y": 1, "z": 5 },

  "solids": [
    { "terrain": "wall",  "pos": [0, 0, 2] },
    { "terrain": "floor", "pos": [1, 0, 2] }
  ],
  "objects": [
    { "type": "box", "pos": [2, 0, 1] }
  ],
  "markers": [
    { "type": "spawn",  "pos": [0, 0, 0], "player": 0 },
    { "type": "target", "pos": [2, 0, 3] }
  ],
  "links": []
}
```

**为什么用 JSON 而不是 Unity 自带格式？**

- 纯文本，Git 能清楚看到改了哪一行
- 多人同时改冲突少
- 程序读写简单
- 出问题可以直接用记事本排查

## 4. 类型注册表：加新东西不用改代码

这是工具最重要的设计。

**每种"能在关卡里放的东西"，都做成一个 `.asset` 文件**，里面写：

| 字段 | 意思 |
|---|---|
| 类型 ID | 唯一名字，比如 `box`（用文字，不用数字） |
| 显示名 | 界面上给策划看的中文名，比如"箱子" |
| 分类 | 属于哪类：实体块 / 物件 / 标记 / 机制 |
| 写在哪一层 | 实体块层 / 物件层 / 标记层 |
| 对应 Prefab | 长什么样 |
| 图标、颜色 | 界面显示用 |
| 特殊项 | 比如坡度需要"朝向"、出生点需要"玩家编号" |

**好处：加新东西时，只新建一个 `.asset`，工具界面自动出现新按钮，代码一行都不用改。**

举例——老板说"加个冰面"：

1. 新建一个 `TileType_Ice.asset`
2. 填 ID = `ice`、分类 = 实体块、绑定冰面 Prefab
3. 打开编辑器工具 → 调色板里自动多出"冰面"按钮

整个过程不碰代码。

## 5. 界面长什么样

```
┌────────────────── 顶部工具条 ──────────────────┐
│  新建  打开  保存  |  校验  |  ▶测试  | 重载    │
├──────────┬────────────────────────┬───────────┤
│          │                        │           │
│  调色板   │      场景视图           │  属性面板  │
│          │   （画关卡的地方）       │           │
│ 按分类    │   显示网格 + 半透明预览  │ 选中格信息 │
│ 分 Tab    │                        │ 朝向/编号  │
│          │                        │           │
├──────────┴────────────────────────┴───────────┤
│  状态栏：鼠标坐标 | 各类型数量 | 校验结果        │
└────────────────────────────────────────────────┘
```

| 区域 | 作用 |
|---|---|
| **顶部工具条** | 新建/保存/校验/测试 等大按钮 |
| **调色板** | 所有可放的东西，点一下选中"当前画笔" |
| **场景视图** | 鼠标在这里画；显示网格和预览 |
| **属性面板** | 显示当前选中格子的信息，可改朝向、编号等 |
| **状态栏** | 实时显示坐标、数量、校验结果 |

## 6. 怎么操作

**鼠标：**

| 操作 | 效果 |
|---|---|
| 左键 | 画（放当前画笔的类型） |
| 右键 | 擦 |
| Shift + 拖动 | 框选矩形区域批量填充 |
| Alt + 左键 | 吸管（把鼠标指到的类型设为当前画笔） |
| 中键拖动 | 平移视角 |
| 滚轮 | 缩放 |

**键盘：**

| 操作 | 效果 |
|---|---|
| 数字键 1-9 | 快速切换画笔 |
| Tab | 切换分类 |
| G | 显示/隐藏网格 |
| Ctrl + Z | 撤销 |

**撤销**：所有操作都要能撤销。做法是每次改数据前告诉 Unity "记住这里"，Unity 就会自动帮我们处理 Ctrl+Z。

## 7. 分层编辑（第四章才需要，先了解）

前三章的关卡是**平的**（只有一层，y 都是 0），简单。

第四章有高度差，所以要能编辑"第几层"。做法：

- 界面上有个**"当前层"选择器**
- **当前层**正常显示，**相邻层**半透明，更远的层隐藏
- 放东西时，放到当前层上

推荐先用**"高度场"方式**：不是一格一格塞，而是像堆沙子一样"抬高/降低"某块区域的高度，更符合直觉。精确逐层编辑作为高级功能以后再补。

> v1 先只做平层，分层放到后面，不要让复杂度一开始就爆炸。

## 8. 校验器：保存前自动检查

保存关卡时自动跑检查，分三级：

| 级别 | 意思 | 例子 |
|---|---|---|
| ❌ 错误 | 必须修，否则关卡非法 | 箱子数 ≠ 抵达点数 |
| ⚠️ 警告 | 可能有问题，提醒一下 | 有按钮没连任何东西 |
| ℹ️ 提示 | 只是告诉你 | 这关有 3 个死锁陷阱格 |

**第一版要做的检查：**

- 出生点数量对不对（第一章要求 1 个）
- 箱子数量 = 抵达点数量
- 有没有东西放在墙上或者悬空
- 连线两端是否存在

**以后再加的检查：**

- 死格提示
- 可达性检查（每个抵达点从出生点能不能走到）
- 可解性验证（需要接一个"求解器"程序）

---

## 9. 测试关卡

- **▶测试按钮**：一键把当前关卡搭出来并运行，直接试玩
- **重载按钮**：游戏运行中，改了关卡数据点一下就能重新加载，不用退出再进

这就是"边跑边改"，能大幅加快调关速度。

---

## 10. 分阶段做（别一次吃成胖子）

| 版本 | 内容 | 能干什么 |
|---|---|---|
| **v1** | 平层编辑：调色板、放置/擦除、矩形填充、JSON 存取、结构校验、▶测试 | 能画第一章的关卡 |
| **v2** | 机制连线编辑 | 能画第二章（彩色按钮） |
| **v3** | 分层 + 坡度朝向 | 能画第四章 |
| **v4** | 可达性、死格、求解器接入 | 关卡质量保障 |

**先把 v1 做完、用起来，再考虑后面。**

## 11. 目录结构

```
Assets/_Project/
  Framework/                    ← 引擎层：和数据、工具相关，和具体玩法无关
    Runtime/                    ← 运行时也要用的代码
      Grid/      网格与坐标
      Level/     关卡数据结构、JSON 读写、校验规则
      Runtime/   加载关卡、生成场景
    Editor/                     ← 只在编辑器里跑的代码
      LevelEditorWindow.cs      主面板
      ScenePainter.cs           场景里画/擦
      PaletteView.cs            调色板
      LevelAsset.cs             内存里的关卡数据（用于撤销）
    Framework.Runtime.asmdef    程序集定义
    Framework.Editor.asmdef     编辑器程序集定义

  Content/                      ← 内容
    Definitions/                类型定义（.asset）与注册表
    Levels/                     关卡文件（.json）
    Prefabs/                    模型模板
```

`Framework` 不认识玩法，`Game`（以后加）才放箱子、按钮这些具体实现。这样工具能被反复复用。

## 12. 需要你拍板的三个选择

我在文档里都给了**推荐值**，你不同意再改：

| 选择 | 推荐 | 理由 |
|---|---|---|
| 分层编辑方式 | **先做高度场笔刷**，逐层笔刷以后加 | 对策划更直观，v1 也用不到 |
| 坡度朝向怎么改 | **快捷键 R 循环 + 属性面板也能选** | 快捷键快，面板易发现 |
| 机制连线 | **先纯手动连线**，颜色自动配对以后加 | 先把通用连线做扎实 |

---

## 13. 一句话总结

> 这个工具就是**一堆放在 `Editor/` 里的脚本 + 一堆 `.asset` 定义文件**。它把鼠标操作变成 JSON 关卡文件，顺便帮你查错、让你一键试玩。它对玩法一无所知，所以能一直用下去。
